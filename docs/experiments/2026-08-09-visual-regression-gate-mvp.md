# 시각 검증 게이트를 만들고 실제 기능 개발에 붙여본다

**목적은 "잘 되는지 보기"가 아니라 "무엇이 예상과 다른지 찾기"입니다.** 특히 시간과, 안 돌아가는 부분.

---

## 1. 무엇을 왜 만드나

코딩 에이전트는 자기가 만든 화면을 못 봅니다. 코드는 읽는데 렌더 결과는 모르죠. 그래서 Lint와 타입 검사와 테스트를 다 통과하고도 레이아웃이 깨진 채로 커밋됩니다.

지금 흔한 대응은 스크린샷을 찍어서 에이전트나 사람에게 보여주는 겁니다. 그런데 스크린샷은 두 가지가 약합니다.

- **작은 기하 변화가 안 보입니다.** 요소가 가로로 40px 밀린 건 축소된 이미지에서 폰트 렌더링 흔들림과 구별이 안 됩니다
- **어디를 고쳐야 할지 안 알려줍니다.** "417,346개 픽셀이 달라졌다"로는 파일을 열 수 없습니다

그리고 더 근본적인 문제가 있습니다. **어떤 결함은 특정 환경에서만 보입니다.** PWA standalone에서만, 다크모드에서만, 320px에서만. 그 환경을 아무도 안 띄워보면 머지하고 배포하고 폰에 설치한 다음에야 발견됩니다. 그 루프가 한 바퀴 도는 데 몇 시간이 걸립니다.

**그래서 만들려는 것**: 커밋 직전에 로컬에서 도는 게이트. 여러 환경을 자동으로 렌더하고, **픽셀이 아니라 DOM에서 뽑은 실측치**로 결함을 찾고, **에이전트가 바로 고칠 수 있는 형태**(요소·파일·수치)로 뱉습니다.

## 2. 게이트의 구조 — 조각 넷

```
① 캡처      Playwright로 라우트 × 환경을 렌더  →  스크린샷 + 레이아웃 JSON
② A층       불변식 검사. 비교 대상 불필요      →  위반이면 하드 실패
③ B층       before/after 레이아웃 diff         →  요소 + 전후값
④ 해석      ②③ 결과 + git diff 를 에이전트에게 →  "지시로 설명되지 않는 것" 목록
```

### ① 캡처

요소마다 이걸 뽑습니다.

```js
{
  key,                                   // 안정적 식별자
  dx: box.x - parent.x,
  gap: box.top - (직전 가시 형제의 bottom ?? parent.top),   // ← 핵심
  w, h,
  color, backgroundColor, fontSize, fontWeight,
  position,                              // fixed/absolute 는 gap 이 무의미
  text                                   // 자기 텍스트 노드만
}
```

**`gap`이 핵심입니다.**

세로 위치를 화면 절대 좌표로 적으면, 위쪽 카드 하나가 커질 때 그 아래 모든 요소의 y가 전부 밀립니다. 의미 있는 변경은 하나인데 수백 개가 "바뀌었다"로 잡히죠.

직전 형제의 아래쪽 끝으로부터의 **간격**으로 적으면 그게 사라집니다. 2번 카드는 "1번 카드 바로 아래 16px"이라는 관계가 그대로거든요. 1번이 커지든 말든요.

**키는 두 전략을 동시에 뽑아두세요.**

- 위치 기반 — `nth-of-type` 경로
- 콘텐츠 기반 — 부분트리 텍스트 해시

**단일 키로는 안 됩니다.** 위치 키는 앞 형제가 삭제되면 뒤 번호가 전부 밀려서 엉뚱한 요소끼리 비교합니다. 콘텐츠 키는 텍스트가 바뀌면 조상 해시까지 흔들립니다. **둘 다 돌려서 적게 잡는 쪽을 채택**하는 것으로 시작하세요.

### ② A층 불변식 — 다섯 개만

비교 대상이 필요 없는 절대 규칙입니다. **baseline도 이전 상태도 필요 없으므로, 새로 만든 화면에서도 작동하는 유일한 층입니다.**

1. 가로 오버플로 — `document.scrollingElement.scrollWidth > clientWidth`
2. 상호작용 요소가 뷰포트 밖으로 이탈
3. `position: fixed` 요소끼리 겹침
4. 텍스트가 컨테이너에서 잘림 — `scrollHeight > clientHeight` + `overflow: hidden`
5. safe-area 침범 — 상호작용 요소가 하단 inset 영역을 침범

**주의: "겹치면 안 된다"는 거짓입니다.** 모달·드롭다운·툴팁·sticky 헤더는 의도적으로 겹칩니다. 예외 셀렉터 목록을 처음부터 두세요.

### ③ B층 레이아웃 diff

before/after를 키로 매칭해서 값이 달라진 요소를 찾습니다.

**조상 체인은 접으세요.** 말단 요소 하나가 커지면 그 조상들이 전부 같이 커집니다. 원인은 말단 하나이므로 그것만 보고하고 나머지는 `+8 ancestors`로 요약합니다.

### ④ 해석 요청

파일로 주고받습니다. **LLM API를 직접 호출하지 마세요.** `request.json`을 쓰고 당신(호스트 에이전트)이 읽고 `verdict.json`을 씁니다.

**프롬프트를 이렇게 쓰는 게 중요합니다.** "의도대로 됐는지 확인해"가 아니라:

> 이 변화 중 당신 지시로 설명되지 않는 것을 나열하세요.

이유가 있습니다. **"의도한 게 됐나"는 물어봐야 새 정보가 없습니다.** 에이전트는 이미 성공했다고 믿고 작업을 끝냈으니까요. 반면 **"지시로 설명 안 되는 게 있나"는 자기가 몰랐던 사실을 캐냅니다.** 자기가 안 건드린 화면이 같이 움직였다는 건 예측할 수 없던 정보입니다.

라벨은 `expected` / `unplanned` / `unexplained` 셋입니다.

**설계 규칙 셋 — 지켜주세요.**

- **`ok`나 `pass` 라벨을 만들지 마세요.** 에이전트에게 통과를 선언할 권한을 주지 않습니다. 설명하거나 못 하거나만 말합니다
- **`unexplained`가 기본값입니다.** 확신이 없으면 사람에게 갑니다
- **채점 기준을 프롬프트에 쓰지 마세요.** 무엇으로 채점하는지 알려주면 채점을 통과하는 답이 아니라 채점에 안 걸리는 답이 나옵니다

## 3. 백엔드는 격리합니다 — 로컬 Supabase를 띄우지 마세요

**비동기로 데이터를 불러오는 화면은 아무것도 안 바꿔도 노이즈가 납니다.** 콜드 로드와 웜 로드에서 하이드레이션 시점이 달라지고, 비동기 리스트가 서로 다른 타이밍에 렌더되면서 래퍼 요소가 삽입되고, 그러면 하위 키가 통째로 어긋납니다.

**결정성이 무너지면 나머지 숫자가 전부 의미를 잃습니다.**

게이트의 범위를 이렇게 정의합니다.

> **주어진 데이터 상태에서 화면이 어떻게 렌더되는가**만 본다. 데이터가 맞는지는 E2E와 백엔드의 일이다.

### 격리 방법 — 이 순서로 시도하세요

이 프로젝트는 external 레이어에서 외부 응답을 전부 도메인 모델로 파싱합니다. **그 경계를 이용합니다.**

#### 안 1 (먼저 시도) — Vite alias로 external 레이어를 갈아끼운다

```ts
// vite.config.ts
resolve: {
  alias: mode === 'visual-gate'
    ? { '@/shared/external': resolve(__dirname, 'src/shared/external/__fixtures__') }
    : {}
}
```

**픽스처는 서버 재시작 없이 쿼리 파라미터로 고르세요.** env로 고르면 픽스처마다 dev 서버를 다시 띄워야 합니다.

```ts
// src/shared/external/__fixtures__/index.ts
const fixture = new URLSearchParams(location.search).get('__fixture') ?? 'normal';
```

→ `http://localhost:5174/board/x?__fixture=empty`

**이 방식이 나은 이유.**

- 실제 앱 전체가 뜬다. 실제 라우터, 실제 레이아웃 셸, 실제 전역 CSS. **문서 수준 불변식이 정확하다**
- Playwright로 그대로 접근한다
- 서비스 워커도, 응답 스키마 흉내도 필요 없다. 도메인 모델을 바로 반환한다
- **로딩·에러가 공짜다.** never-resolving promise를 반환하면 로딩, throw하면 에러. 네트워크 지연 타이밍을 맞추는 것보다 결정적이다
- 인증도 같이 풀린다. 세션 조회가 external 레이어에 있다면 그것도 픽스처로 대체. **Supabase 클라이언트 자체를 속일 필요가 없다**

**대가**: external 레이어의 모든 export에 픽스처 구현이 필요합니다. 다만 도메인 모델이 이 프로젝트의 타입이라 타입 검사가 도와줍니다.

#### 안 2 (안 1이 막히면) — Vitest Browser Mode

⚠️ **현재 vitest config는 unit·integration 둘 다 `environment: 'jsdom'`입니다. jsdom에는 레이아웃 엔진이 없어 `getBoundingClientRect()`가 전부 0을 반환합니다. 그대로는 못 씁니다.**

Vitest 4의 브라우저 모드는 실제 브라우저에서 돌고 viewport·color scheme도 잡힙니다. 다만 이 리포는 vitest `^3.2.6`이라 **업그레이드가 필요**하고, 브라우저 모드에서 `vi.mock`에 제약이 있습니다(module namespace가 sealed. `{ spy: true }` 우회가 필요할 수 있음).

**그리고 더 큰 문제**: 테스트 러너가 마운트한 앱은 실제 앱과 다릅니다. `document.scrollingElement.scrollWidth` 같은 **문서 수준 불변식이 하네스 래퍼 때문에 왜곡**될 수 있습니다. A층 다섯 중 셋이 문서 수준입니다.

#### 안 3 (마지막) — MSW

리포에 `msw` 2.14.6이 설치돼 있긴 합니다. 다만 무겁습니다 — Supabase 세션 처리, 서비스 워커 등록, 응답 스키마 추적. **안 1·2가 둘 다 막혔을 때만.**

## 4. 환경과 데이터 축

### 환경 축 — 커밋 게이트는 넷

조합을 다 보면 폭발합니다. **기준선을 하나 정하고 축을 하나씩만 바꿉니다.** 이 앱은 모바일 우선 PWA이므로 기준선을 모바일로 잡습니다.

| | 조합 |
|---|---|
| E0 | Chromium · 390 · light · browser · 100% |
| E1 | Chromium · 390 · **dark** |
| E2 | Chromium · **320** · light |
| E4 | Chromium · **1280** · light |

(standalone, 텍스트 200%, 다른 엔진은 이번 범위 밖. 다만 **붙일 수 있는지는 확인**해 주세요 — §7 참조.)

### 데이터 축 — 픽스처

| | 픽스처 | 노리는 결함 |
|---|---|---|
| F0 | 정상 | 기준선 |
| F1 | 극단 — 아주 긴 제목, 아주 긴 사용자명, 항목 많음 | 오버플로, 잘림 |
| F2 | 빈 목록 | 빈 상태 레이아웃 |
| F3 | 로딩 중 (never-resolving) | 로딩 UI |
| F4 | 에러 (throw) | 에러 UI |

**조합은 안 돕니다.** 기본 픽스처(F0)에서 환경 넷, 기본 환경(E0)에서 픽스처 다섯.

### 렌더 횟수 — A층과 B층을 다르게 돌립니다

- **A층 불변식**: 비교 대상이 없어서 "after" 한 번만 렌더하면 됩니다 → **전체 매트릭스 8회**
- **B층 diff**: before/after를 둘 다 렌더해야 해서 2배입니다 → **축소 매트릭스(E0·E1 × F0만). before 2 + after 2 = 4회**

**커밋 게이트 1회에 총 10회 렌더**가 기준선입니다.

## 5. 무엇에 돌리나 — 실제 기능 하나

**합성 변경이 아니라 진짜 기능을 하나 개발하세요.** 그래야 진짜 루프가 돕니다.

고르는 기준:

- **UI가 실제로 바뀐다.** 리팩터링이나 타입 정리는 안 됩니다
- **여러 화면에 영향이 갈 수 있다.** 공유 컴포넌트를 건드리면 좋습니다. 부수 효과가 나야 게이트가 할 일이 생깁니다
- **한 번에 끝나지 않을 만한 크기.** 두세 커밋 정도

무엇을 골랐는지, 왜 골랐는지 보고해 주세요.

**그리고 그 기능을 실제로 개발하면서 매 커밋마다 게이트를 통과시키세요.** 게이트가 뭘 말하는지, 그게 도움이 됐는지 방해가 됐는지가 이 실험의 답입니다.

## 6. 측정할 것

### 시간 — 이게 제일 중요합니다

```
격리 셋업 (픽스처 작성)          __ 분   ← 일회성. 파일 __개
dev 서버 기동                    __ 초   (상주시킬 수 있나?)
라우트 1개 × 환경 1개 캡처        __ 초
커밋 게이트 1회 전체 (10회 렌더)   __ 초
  ├ 캡처                        __
  ├ A층                         __
  ├ B층 diff                    __
  └ 해석 요청 왕복               __
```

**판단 기준**: 커밋마다 30초면 쓸 만합니다. 2분이면 사람들이 끕니다. 실제로 몇 초인지가 이 도구의 생사를 정합니다.

### 잡았나 / 방해했나

- 게이트가 **실제 결함을 잡은 적**이 있나? 몇 번?
- **오탐이 몇 번**이었나? 그게 작업을 얼마나 방해했나?
- 해석 단계에서 당신(에이전트)이 **잘못 판정한 적**이 있나?

### 예상 못 한 문제 ← 이게 진짜 목적

무엇이든 기록해 주세요. 사소해 보여도요.

## 7. 아마 걸릴 것들 (전부 확인은 안 했습니다)

미리 답을 주진 않겠습니다. **부딪히면 어떻게 풀었는지 기록해 주세요.**

- **external 레이어의 경계가 실제로 얼마나 넓은가.** ★ 안 1의 성패를 가릅니다. **픽스처를 만드느라 파일 몇 개를 새로 썼고 몇 분 걸렸는지 반드시 재세요.** 이 숫자가 곧 이 게이트의 진입 장벽입니다
- **인증.** 세션 조회가 external 레이어 안에 있는지, 아니면 Supabase 클라이언트를 직접 부르는 코드가 흩어져 있는지. 후자면 alias만으로 안 됩니다
- **쿼리 파라미터로 픽스처 전환이 실제로 되는지.** 라우터가 알 수 없는 쿼리를 떨어뜨리지는 않는지
- **어느 라우트를 찍을 것인가.** 에이전트는 자기가 어느 화면을 고치는지 모릅니다. manifest에 목록을 두고 작업 시작 시 선언하는 게 지금 안인데, 실제로 굴러가는지
- **before를 언제 찍나.** 편집 후에 찍으면 늦습니다. `git stash` 후 렌더할 수도 있고, 직전 커밋을 worktree로 띄울 수도 있습니다. **어느 쪽이 싼지 실측해 주세요**
- **비결정적 콘텐츠.** D-day 숫자, 상대 시간("3분 전"), 랜덤 아바타. 픽스처로 고정되는지, 아니면 앱 안에 남아 있는지. 아무것도 안 바꾸고 두 번 찍어서 자동으로 찾아낼 수 있는지
- **텍스트 200%를 어떻게 흉내내나.** Playwright에 네이티브 API가 없습니다. CSS 주입? CDP 줌?
- **`display-mode: standalone`과 `env(safe-area-inset-*)`.** 브라우저에서 흉내낼 방법이 있는지. 없으면 CSS 변수 주입으로 대체 가능한지
- **요소 → 파일:줄번호 (선택).** dev 모드에서 babel이 React fiber에 `_jsxFileName`/`_jsxLineNumber`를 심어둡니다. `react-grab`이나 `dom-to-fiber-utils`로 뽑을 수 있고요. **이 리포의 Vite 설정에서 실제로 되는지 확인해 주세요.** 되면 게이트 출력이 훨씬 쓸 만해집니다 (`h2 in PostCardContent (…/PostCardContent.tsx:31)`). 안 되면 왜 안 되는지만 적어주세요
