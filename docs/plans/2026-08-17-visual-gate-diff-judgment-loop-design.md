# Visual gate — diff→판정 루프 설계 (B층의 심장)

날짜: 2026-08-17
브랜치: `BumgeunSong/visual-gate`
선행: `2026-08-13-visual-gate-baseline-env-design.md` (baseline·환경), `2026-08-12-dom-diff-matcher-plan.md` (diff 엔진), `2026-08-09-visual-regression-gate-mvp.md`

## 이 문서가 뒤집는 전제

선행 설계는 A층 게이트를 먼저 짓는 순서였다. 그 순서는 지금도 맞다. A층은 baseline 없이 바로 값을 내고, Phase 2에서 `?__fixture=`로 진짜 상태 페이지까지 올라왔다.

그런데 A층을 실제 화면에 써보니 한계가 구조적이다. 절대 규칙은 넷뿐이다. 가로 오버플로, 인터랙티브 요소의 뷰포트 이탈, 고정 요소 겹침, 텍스트 클립. 반면 현실의 회귀는 끝이 없다. 색이 틀어지고, 간격이 좁아지고, 요소가 어긋나고, 폰트가 줄고, 20px 밀린다. 규칙을 하나 더 넣어도 한 조각만 덮고 꼬리는 남는다. 규칙이 던지는 질문은 "이 화면이 유효하지 않은가"인데, 실제 버그는 대개 멀쩡히 유효한 화면이 그냥 틀린 경우다.

그래서 게이트의 심장을 baseline diff로 옮긴다. diff는 규칙 목록에 갇히지 않고 모든 변경을 잡는다. 커버리지 문제를 정면으로 푼다.

대신 diff는 반대편 문제를 떠안는다. 모든 변경을 잡으니, 회귀뿐 아니라 방금 내가 의도한 편집도 잡고 비결정 노이즈도 잡는다. 스냅샷 테스트가 여기저기서 `--update-all` 습관으로 썩는 이유가 이것이다. diff가 전부에 발화하면 사람도 에이전트도 무지성 수락을 배우고, 게이트는 조용히 죽는다.

문제를 없앤 게 아니라 옮긴 셈이다.

```
절대 규칙:  어려운 문제 = "규칙을 충분히 열거하기"      (커버리지)
baseline diff:  어려운 문제 = "발화한 diff가
                 회귀인가 의도인가 판정하기"            (판정)
                + "비결정 churn 억제"                   (노이즈)
```

노이즈 쪽은 이미 절반 이겼다. DOM 트리 diff가 픽셀 diff보다 나은 지점이 바로 여기다(안티에일리어싱·폰트 힌팅 잡음이 없다). 결정성 작업(시계·RNG 동결, `roundTree`, N=3 안정, `data-vg-ready`)이 그 토대다. **남은 건 판정이고, 이 실험의 성패가 거기 달렸다.** 이 문서는 그 판정 루프를 설계한다.

## 5각도 리뷰 반영 (2026-08-17)

초안을 5각도 서브에이전트 리뷰(아키텍처·적대·결정성·인식론·YAGNI)에 걸었다. 핵심 아이디어인 git diff × sourceId 교차는 다섯 모두 견고하다고 봤다. 문제는 배선과 과장에 있었고, 세 각도(적대·결정성·인식론)가 서로 모른 채 같은 결론에 닿았다.

**메타 발견: 이 설계는 놓침(거짓 음성) 쪽으로 기운다. 게이트한테는 그게 치명적인 방향이다.** 초안은 파일 단위 매칭의 "오탐보다 누락이 안전하다"를 안전한 쪽이라고 적었는데 반대다. 초록불인데 실은 눈먼 게이트는 없느니만 못하다. 없는 신뢰를 지어내기 때문이다. 아래 수정은 전부 explained 판정을 좁혀서 놓침을 줄이는 방향이다.

반영한 수정(괄호는 반영된 절):
1. **조상 cascade 남용은 핵심 가치를 통째로 무너뜨린다** (판정기 절). 컨테이너 파일 하나만 고쳐도 그 아래 서브트리 전체가 explained로 면죄되고, 원격작용 회귀가 조용히 통과한다. 조상 편집은 자식이 밀리는 리플로우형 변화만 설명하게 하고, 자식의 새 절대위반이나 색·폰트·간격 변화는 절대 면죄하지 않는다.
2. **파일 단위는 너무 거칠다** (판정기 절). 한 파일이 노드를 여럿 만드니, 한 줄만 고쳐도 그 파일의 다른 부분 회귀까지 면죄된다. 줄 범위 매칭은 선택이 아니라 필수로 올린다.
3. **소스 diff가 없으면 게이트를 우회한다** (설계 다이얼 절). 전역 CSS·토큰·의존성·데이터 변경은 컴포넌트 파일을 안 건드려 전부 unexplained가 되고, 구조가 안 깨진 것은 Tier 2 경고로 끝나 아무도 안 막힌다. 같은 종류 unexplained가 무더기로 나오면서 소스 diff가 비면, 경고가 아니라 차단이나 리뷰로 올린다.
4. **baseline 레포 커밋 결정을 철회한다** (baseline 절). 시스템 폰트에 한글이라 macOS와 리눅스의 글리프 메트릭이 줄 단위로 갈린다. 커밋한 baseline은 다른 머신에서 다 깨진다. 8차 결정(per-dev 로컬)이 옳았다. 프로토타입은 `git stash`로 before/after만 떠서 baseline 저장 자체를 건너뛴다.
5. **matchTrees가 judge와 안 맞는다** (아래 절). judge는 노드 객체·조상·노드별 sourceId를 가정하는데, matchTrees는 라벨 문자열만 낸다. treematch/gate.mjs에 sourceId와 조상 사슬을 실어야 judge를 짤 수 있다. "diff 엔진 완성"은 judge 관점에선 거짓이다.
6. **자기 판정 과신을 낮춘다** (Tier 2 절). 사례 다섯 건으로 아키텍처를 못박은 건 과했다. self-report는 git diff가 뒷받침할 때만 경고를 눌러주는 보조로 강등한다.
7. **커버리지 숫자는 측정이 아니라 추정이다** (커버리지 절). 분모 13은 게이트에 유리하게 고른 것이고 11/13은 아직 안 돌려본 추정이다. 실제 회귀로 재현하기 전까지 추정이라고 표기한다.
8. **verdict 빈틈** (3단 verdict 절). matchTrees의 다섯 범주를 3단에 매핑하고, ambiguous 처리와 subtractViolations의 위반 identity를 명시한다.

## 이미 있는 것과 없는 것

```
CAPTURE          matchTrees          판정              verdict + baseline
gate.mjs    →    treematch.mjs   →   (없음)       →    (없음)
(있음)           (있음)
```

`matchTrees(baseline, current)`는 이미 쓸 만한 delta를 낸다. `{ changed, moved, added, removed, ambiguous }`에 노드별 `sourceId`가 붙는다. 신원(tag/role/contractKey/shape/text)과 metric을 따로 저장하니 스타일이 바뀌어도 매칭이 안 깨진다.

다만 리뷰가 짚었듯, matchTrees의 출력은 `label()`로 이미 문자열이 된 상태다. 노드 객체도, 부모 포인터도, 노드별 sourceId 필드도 그 시점엔 없다. judge가 쓰려면 treematch와 gate.mjs를 고쳐서 각 delta에 sourceId와 조상 사슬을 실어야 한다. 이 배선을 빼면 아래 판정기는 못 짠다. 즉 엔진이 판정까지 끝나 있는 건 아니다.

없는 것은 diff 다음 전부다. baseline 저장소가 없고, delta를 verdict로 바꾸는 판정이 없다. 지금 `diff.mjs`는 delta를 찍기만 하고 verdict도 exit code도 없다.

## 핵심 아이디어: 소스 없는 변경은 회귀다

판정은 delta 하나당 질문 하나로 줄어든다.

> 저자의 코드 변경이 이 DOM 변경을 설명하는가?

두 반쪽 다 기계가 읽는 형태로 이미 있다.

- **소스 diff**: `git diff`가 건드린 `file:line` 집합을 준다(저자가 `MentionableInput.tsx`를 고쳤다).
- **DOM diff**: 바뀐 노드마다 `sourceId = file:line:col`이 붙는다. 실측으로 확인했다. 예: `src/comment/components/MentionableInput.tsx:134:6`.

둘을 교차한다.

| DOM 노드 변경? | 그 소스 파일 건드림? | 분류 |
|---|---|---|
| 예 | 예 | **explained** (설명됨): 의도, 허용 |
| 예 | **아니오** | **unexplained** (설명 안 됨): 회귀의 지문 |

unexplained 행이 전부다. 버튼 색을 바꿨으면 버튼의 소스 줄도 바뀌었으니 explained다. 그런데 그 변경이 등록 버튼을 화면 밖으로 밀었다면, 등록 버튼의 DOM은 바뀌었는데 그 소스는 건드린 적이 없으니 unexplained다. 이게 원격작용이다. 손대지도 않은 곳이 딸려 움직인 것. 타입체크와 유닛 테스트가 못 보는 바로 그 회귀를, 무엇이 밀렸는지 소스 좌표까지 짚어서 잡는다.

판정이 온전히 결정적이라 게이트 안에 둔다. 선행 설계의 결정(`결정적층 = 게이트, VLM은 밖`)과 결이 같다.

## 3단 verdict

unexplained라고 다 같은 죄는 아니다. 잔여를 등급으로 나눈다.

- **Tier 1 — BLOCK (결정적, 고신뢰).** current에는 있고 baseline에는 없는 새 절대 규칙 위반(오버플로/화면밖/겹침/클립). 의도와 무관하게 틀렸다. 이건 A층인데 차분(differential)으로 만든다. 원래 있던 오버플로가 무관한 변경을 막던 문제가 사라진다.
- **Tier 2 — REVIEW (표면화, 기본 비차단, loud-pass).** 절대 위반은 아니지만 unexplained인 delta. 손 안 댄 곳에서 노드가 이동·변경·등장했다. 소스 귀속과 함께 드러낸다. 기계 교차가 못 가른 이 잔여는 아래 프로토콜로 되묻는다. 기본은 경고지 루프를 오차단하지 않는다.
- **Tier 3 — PASS (승격 가능).** 모든 delta가 건드린 파일로 설명되고 새 위반이 없다. `current → baseline` 승격을 제안한다.

여기서 A층의 처지를 보라. 절대 규칙이 주 메커니즘이 될 수 없다는 진단은 옳았다. 이 설계에서 절대 규칙은 diff 잔여를 거르는 이차 고신뢰 분류기로 내려앉는다. 더 작고 정직한 역할이다. 주력은 baseline diff고, 절대 규칙은 설명 안 된 꼬리만 본다.

**다섯 범주를 3단에 매핑.** matchTrees는 `changed/moved/added/removed/ambiguous`를 낸다. 앞의 넷은 explained/unexplained 축으로 흘려보낸다. `ambiguous`는 다르다. 매처가 스스로 귀속을 포기한 쌍이라(같은 모양 형제가 뒤섞인 경우) 별도 버킷으로 뺀다. 절대 차단하지 않고 "귀속 불가"로만 표기한다. comments-long-thread는 같은 모양 `CommentRow`가 여럿이라 ambiguous가 구조적으로 나온다는 점을 감안한 것이다. 그리고 축의 우선순위: 위반 축이 explained 축을 이긴다. 건드린 파일 안이라도 새 절대 위반이면 Tier 1이다.

## 판정기 (심장, 의사코드)

```javascript
function judge({ baseline, current, touchedFiles }) {
  const deltas = matchTrees(hashTree(baseline.tree), hashTree(current.tree));

  // explained = 노드나 그 조상이 저자가 편집한 파일에 속함.
  // 단 조상으로 인한 면죄는 리플로우형 변화(위치 이동: moved, gapTop, widthRatio)에만.
  // 자식의 새 절대위반이나 색·폰트·간격 변화는 조상 편집으로 설명되지 않는다.
  // hasLine = 파일+줄 범위 일치(필수), hasFile = 파일만 일치(조상 cascade용).
  const isExplained = (node, delta) => {
    if (touchedFiles.hasLine(node.sourceId)) return true;
    const ancestorTouched = node.ancestors.some((a) => touchedFiles.hasFile(a.sourceId));
    return ancestorTouched && isReflowShaped(delta);
  };

  const unexplained = allChangedNodes(deltas).filter((n, d) => !isExplained(n, d));

  // Tier 1: 차분 A층. 위반 identity = (rule, 위반 요소의 sourceId).
  // 좌표는 표시용이라 identity에서 뺀다(좌표를 키에 넣으면 1px만 밀려도 새 위반으로 오판).
  const newViolations = subtractViolations(current.violations, baseline.violations);

  if (newViolations.length) return { tier: 'BLOCK', newViolations, unexplained };
  if (unexplained.length)   return { tier: 'REVIEW', unexplained };
  return { tier: 'PASS', deltas };
}
```

견고성을 위한 선택 둘. 초안에서 리뷰가 뒤집은 지점이다.

- **줄 범위까지 본다(필수).** 초안은 파일 단위로만 교차하고 줄 범위는 선택이라 적었다. 그런데 이 코드베이스는 한 파일이 노드를 여럿 만든다. `CommentRow.tsx` 하나가 네 노드(53·54·73·85줄)를 낸다. 파일 단위면 73줄만 고쳐도 나머지 세 줄의 회귀까지 면죄된다. 그래서 노드 자신의 매칭은 파일+줄 범위(`hasLine`)로 좁힌다. `sourceId` 줄 번호가 위쪽 편집에 밀리는 약점은 남지만, 파일 단위만 쓰는 구멍이 훨씬 크다.
- **조상 cascade는 리플로우형만 설명한다.** flex 컨테이너를 고치면 자식이 정당히 밀린다. 그 밀림은 조상으로 설명된다. 문제는 초안이 조상 매칭을 파일 단위로만 걸어서, 컨테이너 파일 하나가 서브트리 전체를 면죄한 것이다. `CommentList.tsx`는 댓글 숲 전체의 조상이라, 한 줄만 고쳐도 그 아래 등록 버튼이 화면 밖으로 밀린 것까지 explained가 됐다. 게이트가 잡으려던 바로 그 버그다. 그래서 조상에 의한 면죄는 리플로우형 delta(moved, gapTop, widthRatio)에만 준다. 자식의 새 절대위반이나 색·폰트·간격 변화는 조상이 설명하지 못한다. 여전히 unexplained로 남는다.

### 파생 스코프가 선언 스코프를 이긴다

스코프를 정하는 길은 둘이다. 에이전트한테 "나는 X만 바꾼다"고 선언시키거나(선언 스코프), 실제 `git diff`에서 건드린 파일을 뽑거나(파생 스코프). 이 설계는 파생을 고른다. 근거는 실측이다. 채점 기준을 프롬프트에 보여주면, 채점을 통과하는 답이 아니라 채점에 안 걸리는 답이 나온다. 스코프 선언을 쓰는 쪽에 판정 규칙을 보여주면 스코프가 넓어진다. 선언 스코프는 게임당한다.

파생 스코프는 이 함정에 안 걸린다. 스코프가 자기보고가 아니라 실제 코드 diff에서 나오니, 스코프를 부풀리려면 코드를 진짜로 안 건드린 척해야 하는데 그럴 수 없다. 규칙을 숨기는 게 아니라, 판정의 입력 자체를 에이전트의 말이 아닌 기계가 읽는 사실(git diff × sourceId)로 두는 것이다.

## 잔여를 에이전트에게 물을 때 (Tier 2 프로토콜)

기계 교차가 못 가른 잔여가 Tier 2로 떨어진다. 절대 위반은 아니지만 unexplained인, 구조가 안 깨진 delta다. 이걸 누구에게 어떻게 묻느냐로 결과가 갈린다. 실측에서 얻은 네 가지를 프로토콜로 박는다. 단, 리뷰가 지적한 대로 이 채널은 어디까지나 보조다. 뒤의 강등 문단을 함께 본다.

- **질문을 뒤집는다.** "의도대로 됐는지 봐라"는 정보가 없다. 에이전트는 이미 성공했다고 믿고 끝냈으니 그렇다고 답한다. 대신 "이 변화 중 네 지시로 설명 안 되는 걸 나열해라"로 묻는다. 그러면 손 안 댄 화면이 딸려 움직였다는, 자기 머릿속에 없던 사실이 나온다.
- **통과 라벨을 주지 않는다.** `ok`나 `pass`가 아니라 `expected` / `unplanned` / `unexplained` 셋뿐이고 기본값은 `unexplained`다. 통과를 선언할 권한을 주지 않고, 설명하거나 못 하거나만 말하게 한다.
- **채점 기준을 안 보여준다.** unexplained가 곧 차단이라고 알려주면, 채점을 통과하는 답이 아니라 안 걸리는 답이 나온다. 위 파생 스코프와 같은 실패다. 분류 규칙은 숨기고 delta 목록만 넘겨 귀속만 받는다.
- **자기 세션이 남보다 낫다(반직관).** 에디터 교체에서 높이가 18px 준 부작용을, 그 작업을 한 세션은 `unplanned`로 정확히 찍었고 맥락 없는 판정자는 `expected`로 흘렸다. 이유는 이렇다. 자기는 자기가 안 한 일을 안다. "나는 높이를 건드린 적 없다"를 근거로 쓴다. 남은 diff만 보는 판정자는 "에디터를 바꿨으면 높이도 바뀔 만하지"로 넘긴다. 작업 요약을 넘겨줘도 못 따라잡았고 오히려 나빠졌다. (사례 다섯 건짜리 일화지 통계는 아니다.)

**다만 이걸 아키텍처로 못박지는 않는다.** 리뷰가 짚었듯 사례 다섯 건은 "자기가 알아챈 경우"만 모은 표본이라, 정작 위험한 실패(자기가 저지른 회귀를 스스로 정당화하는 경우)는 이 표본에 안 잡힌다. 게다가 `expected` 라벨 자체가 "이 변화는 내 의도로 설명된다"는 성공 판정이라, 이 프로젝트가 불신하기로 한 자기보고가 뒷문으로 들어온다. 그래서 self-report는 판정을 대체하지 않고, git diff가 뒷받침할 때만 경고를 눌러주는 색깔 정도로 쓴다. 에이전트가 `expected`라 해도 diff가 unexplained면 diff가 이긴다. 그런데 diff가 explained라면 애초에 기계 층이 이미 통과시켰으니 self-report가 필요 없다. 결국 새 판정자를 스폰하거나 요약을 핸드오프하는 대신 작업 세션 안에서 묻되, 그 답을 verdict로 삼지는 않는다.

이게 "gate over prompt"와 안 부딪히는 이유. 게이트가 거부하는 건 성공의 자기보고("됐어? 응")다. 그건 평가라 정당화된다. 여기서 받는 건 행동 경계의 자기보고("나는 높이를 안 건드렸다")다. 그건 자기 행위에 대한 사실이라 정보다. 다만 그 사실의 진짜 버전은 이미 git diff에 있다. 그래서 self-report는 git diff의 보완재지 대체재가 아니다.

## baseline 저장과 승격

여기가 리뷰에서 내 결정이 뒤집힌 자리다. 초안은 baseline을 레포에 커밋하자고 했다. 근거로 "DOM 트리는 머신 간 동일하다"를 들었는데 틀렸다.

이 앱은 웹폰트를 안 쓰고 OS 기본 폰트를 쓴다. 화면 글자는 한글이다. macOS는 Apple SD Gothic Neo, 리눅스 CI는 Noto Sans CJK로 폰트가 다르다. 폰트가 다르면 글자 폭과 줄바꿈이 달라지고, 줄바꿈이 달라지면 요소 높이가 통째로 수십 px씩 달라진다. 허용오차 1px을 한참 넘는다. 즉 내 맥에서 뜬 baseline을 리눅스 CI에서 비교하면 멀쩡한 화면도 죄다 회귀로 뜬다. 게다가 저장값이 소수점 끝까지 raw float라 같은 머신에서도 미세하게 흔들리고, Playwright도 caret 범위라 크롬 버전이 오르면 baseline이 다 깨진다.

그래서 결정을 되돌린다.

- **프로토타입에선 baseline 저장소를 안 만든다.** `git stash`로 before를 뜨고 stash pop 후 after를 뜬다. 지금 `diff.mjs`가 이미 before/after 두 캡처를 비교하니, 저장소 없이 판정 아이디어를 바로 시험할 수 있다.
- **공유가 필요해지면** 8차 결정(per-dev 로컬 재생성, gitignore)으로 돌아간다. 같은 머신 self-compare라 폰트 문제가 없다.
- **그래도 커밋하려면** 조건을 다 갖춘 뒤에만 한다. CI 고정 OS 이미지에서 캡처, 한글 폰트를 하네스 CSS에 직접 박기, raw float 대신 `roundTree` 투영값 저장, Playwright 정확한 버전 고정과 baseline에 browserVersion 기록. 하나라도 빠지면 커밋 baseline은 안 된다.

승격 자체(무지성 `--update-all`을 끊는 장치)는 유지할 가치가 있지만, 저장소가 없으면 승격도 없다. 그러니 판정이 실제 회귀로 검증된 뒤로 미룬다. 원칙만 적어둔다. 승격은 게이트가 Tier 3로 본 캡처만, 먼저 explained delta 목록을 찍고 나서, 사람이 그 목록을 읽고 받아들인다.

## 두 워크드 예제

**의도: 버튼 색을 보라로.** 소스 diff가 `CommentActions.tsx`를 건드림. DOM diff: `changed` 노드 하나 `button color rgba(37,99,235) → rgba(124,58,237)`, sourceId `CommentActions.tsx:44:6`. 파일과 줄을 건드림 → explained. 새 위반 없음 → Tier 3 PASS, 승격 제안.

**회귀: prove-value 실험의 min-width 오버플로.** 소스 diff가 `MentionableInput.tsx`만 건드림. E2(320px)에서 DOM diff: 등록 버튼 `moved` + `interactive-outside-viewport` at `[392,408]`. 버튼 sourceId가 건드린 파일 안이지만, baseline에 없던 새 절대 위반이라 Tier 1 BLOCK. 설령 안 건드린 파일이었어도 Tier 1이다. 위반 축이 explained 축을 이긴다. 어느 쪽이든 잡힌다.

## 구현 단계

프로토타입과 완성본을 나눈다.

**프로토타입(이번 세션 목표): 실제 회귀 하나에 판정 아이디어를 돌려본다.**
- `git stash`로 before 캡처, pop 후 after 캡처.
- `git diff --name-only`로 `touchedFiles`(파일+줄 범위).
- treematch에 sourceId·조상 사슬 싣기(judge가 어차피 필요로 하는, 버릴 게 아닌 유일한 실작업).
- `diff.mjs`에 붙여 unexplained delta를 소스 귀속과 함께 찍기. 여기서 멈춘다. exit code도 tier도 아직 없다.
- 위 조상 cascade 좁힘과 줄 범위 매칭은 코드가 굳기 전인 지금부터 넣는다. 나중에 끼우기보다 싸다.
- 32건 커밋 이력에서 시각 회귀 서넛을 골라 이 프로토타입에 재현시켜 본다. 이게 커버리지 숫자를 추정에서 측정으로 바꾸고, 조상·파일 구멍이 실제로 무는지도 같이 확인한다.

**완성본(프로토타입이 값을 증명한 뒤): 원자 커밋으로.**
1. `feat`: 차분 A층 — `subtractViolations`로 새 위반만 계수. 위반 identity는 (rule, sourceId).
2. `feat`: `judge()` 3단 verdict + `check.mjs` exit code(Tier 1 → exit 1; Tier 2/3 → 0). Tier 2 잔여는 unexplained 라벨로 찍기만 하고, 자기 판정은 위 프로토콜대로 작업 세션이 소비하지 게이트가 자동 판정하지 않는다.
3. `feat`: baseline 저장소 + 승격 — 단, 위 baseline 절의 조건(고정 이미지·폰트·투영값·버전)을 갖춘 뒤에만.
4. `test`: 판정기 유닛 테스트(explained/unexplained/조상 cascade/줄 범위/차분 위반).

판정 루프가 서면, 다음 커버리지 투자는 규칙이 아니라 픽스처 상태 축이다(아래 커버리지 절). comments-long-thread 한 화면을 정상·극단·빈·로딩·에러로 늘리는 게 A층 규칙 추가보다 많이 잡는다.

## 이 게이트가 실제로 몇 개나 잡나 (커밋 이력 역산)

주의: 아래 숫자는 측정이 아니라 추정이다. 판정 층이 아직 안 돌았으니 "돌렸더니 잡혔다"가 아니라 "돌리면 잡힐 것으로 보인다"에 가깝다. 프로토타입으로 실제 재현하기 전까지는 방향을 정하는 참고로만 쓴다.

DWF 이력에서 시각 결함으로 되돌리거나 고친 커밋은 32건이다. 그중 상당수는 Playwright E2E가 이미 잡는 영역이다(클릭이 안 먹힘, 화면이 안 뜸, 라우팅이 틀림). 게이트 범위를 E2E로는 단언 못 하는 순수 시각 결함으로 좁히면 분모가 13이 된다. 이 분모는 게이트에 유리하게 고른 것이라, 숫자를 인용할 때 이 조건을 같이 달아야 한다.

| 구성 | 잡히는 수(추정) |
|---|---|
| 보편 규칙만 (오버플로·이탈·겹침·잘림·대비) | 5 / 13 |
| + 앱 고유 규칙 + 상태 시나리오(로딩·에러·빈·극단 콘텐츠) | 11 / 13 |

커버리지를 올린 지렛대는 규칙이 아니라 상태 시나리오였다. 규칙을 더 넣기보다 같은 화면을 더 많은 데이터 상태로 렌더하는 쪽이 많이 잡는다. 이게 이 문서의 전제(baseline diff + 픽스처 > 절대 규칙)와 같은 방향이고, 판정 루프 다음의 투자처도 여기다. A층 규칙을 늘리지 말고 픽스처 상태 축(정상·극단·빈·로딩·에러)을 늘려라. 다만 11/13이 추정인 만큼, 프로토타입으로 서넛을 재현해 측정으로 바꾼 뒤에 이 방향을 확정한다.

조합은 안 돌린다. 기본 픽스처에서 환경 전부, 기본 환경에서 픽스처 전부. 선행 설계의 "환경을 곱하지 말라"를 픽스처 축으로 넓힌 것이다.

## 사람이 남는 자리

새 디자인이 아름다운지, 카피가 자연스러운지, 의미가 맞는지는 회귀가 아니라 창작 판단이라 결정적 게이트 밖이다. 그리고 baseline이 처음부터 틀리면 게이트는 그 오류를 영원히 보존한다. 쓰레기 baseline이면 영원히 쓰레기다. 그래서 baseline 승인은 사람 몫으로 남는다. 게이트는 회귀를 막지, 좋은 디자인을 만들지 않는다. 승격 때 delta를 사람이 읽는 것이 이 자리를 최소한으로 지키는 장치다.

## 설계 다이얼과 리스크

- **스코프 입도**(파일 / 줄 / 조상 cascade). 놓침과 오탐 비율을 가장 크게 좌우한다. 기본은 줄 범위 + 리플로우형만 면죄하는 조상 cascade. 너무 빡빡하면 그때 푼다.
- **소스 diff 부재 케이스**(전역 CSS·토큰·의존성 범프·데이터 변경). 컴포넌트 파일을 안 건드려 전부 unexplained가 된다. 초안은 이걸 "폴백" 정도로 적었는데, 리뷰가 짚었듯 이때 게이트가 통째로 우회된다. 구조 안 깨진 변화는 Tier 2 경고로 끝나 아무도 안 막히고, 남는 건 부족하다고 인정한 절대 규칙 5개뿐이다. 그래서 규칙을 둔다. 같은 종류 unexplained(예: 색 변화)가 무더기인데 소스 diff가 비면, 경고가 아니라 차단이나 리뷰로 올린다.
- **Tier 2 홍수 = 스냅샷 썩음의 재림.** 큰 리팩터(이름 변경·파일 이동)는 정당한 변경인데도 unexplained delta를 무더기로 쏟아 Tier 2를 시끄럽게 한다. 그러면 사람이 Tier 2를 흘려보는 법을 배우고, 그 홍수에 숨은 진짜 회귀가 묻힌다. 완화: 같은 모양 대량 이동은 리뷰 항목 하나로 접고, Tier 2 홍수는 경계를 낮추는 게 아니라 높이는 신호로 다룬다.
- **sourceId 없는 노드.** 라이브러리 마크업이나 SVG 리프처럼 `data-vg-id`가 없는 노드가 있다. 실측 캡처에서 83개 중 8개가 그렇다. 이 노드는 자기 파일로 매칭이 안 돼 조상 cascade에만 기댄다. 규칙: sourceId 없는 노드 + 새 절대위반은 그래도 Tier 1, sourceId 없는 노드 + 구조 안 깨짐은 우연한 조상으로 면죄하지 않는다.
- **git diff 기준을 고정한다.** `git diff` 그냥 쓰면 staged/unstaged/브랜치 기준이 다 다른 집합이다. `git merge-base origin/main`부터 HEAD까지에 워킹트리를 더해 "이 브랜치가 건드린 전부"로 스코프를 잡는다.
- **baseline 노후화.** 작은 승격이 쌓이면 baseline이 드리프트한다. 승격 때 delta 리뷰가 방어선이지만, 사람이 실제로 diff를 읽어야 성립한다.

## 한 줄 요약

matchTrees가 탐지기, git diff × sourceId가 판정자, 차분 A층이 고신뢰 백스톱, VLM과 사람은 애매한 꼬리만 만진다. 단 설명 판정을 좁게 잡아야 한다. 헐거우면 놓치고, 놓치는 게이트는 없느니만 못하다. 이게 실제 변경에 돌릴 루프다.
